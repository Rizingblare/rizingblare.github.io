격리 수준은 “트랜잭션을 얼마나 잠글 것인가”보다 서로의 변경을 어떤 규칙으로 관찰하게 할 것인가입니다

트랜잭션 격리 수준은 여러 트랜잭션이 동시에 실행될 때 각 트랜잭션이 어떤 데이터 버전을 볼 수 있고, 어떤 동시 실행 결과를 허용할지 정합니다. 높은 격리는 모든 일을 단순히 직렬로 실행한다는 뜻이 아니라, 결과가 어떤 직렬 스케줄과 동등하도록 보장하거나 그에 가까운 관찰 규칙을 제공합니다.

성능동시에 더 많이 진행

서로 충돌하지 않는 읽기와 쓰기는 가능한 한 함께 진행해 처리량과 응답성을 높입니다.

일관성허용할 관찰을 제한

더티 리드, 반복 불가능 읽기, 팬텀 리드와 더 복잡한 이상 현상을 제한합니다.

응용 책임실패와 재시도를 설계

높은 격리에서도 직렬화 실패나 교착 상태로 트랜잭션이 중단될 수 있으므로 안전한 재시도가 필요합니다.

제품 이름만 보고 보장을 단정하지 않기같은 “Repeatable Read” 이름도 DBMS 구현에 따라 스냅샷 범위, 잠금, 팬텀 방지, 갱신 충돌 처리 방식이 다를 수 있습니다. 격리 수준 이름과 실제 제품 문서를 함께 확인해야 합니다.

Anomalies · Read the schedule

이상 현상은 이름보다 두 트랜잭션의 시간 순서를 그려야 정확히 구분됩니다

이상 현상핵심 패턴문제가 되는 이유단순한 예
더티 리드T1이 아직 커밋하지 않은 값을 T2가 읽음T1이 롤백하면 T2는 존재하지 않았던 값을 바탕으로 행동함출금 중간 잔액을 다른 요청이 읽음
반복 불가능 읽기T1의 같은 행 두 번 읽기 사이에 T2가 수정·커밋한 트랜잭션 안에서 같은 질문의 답이 달라짐주문 금액을 두 번 읽었더니 값이 변함
팬텀 리드T1의 같은 조건 조회 사이에 T2가 조건을 만족하는 행을 삽입·삭제행 집합·집계 결과가 달라짐“재고 부족 상품 수”가 같은 트랜잭션 안에서 증가
갱신 분실T1·T2가 같은 이전 값을 읽고 각자 계산한 뒤 나중 쓰기가 앞선 쓰기를 덮음둘 중 한 변경이 사라짐조회한 잔액에 각각 +10을 계산해 마지막 UPDATE가 덮음
쓰기 스큐T1·T2가 같은 조건을 읽지만 서로 다른 행을 수정해 전체 제약을 깨뜨림행 단위 충돌은 없어도 여러 행에 걸친 불변식이 깨짐두 당직 의사가 서로 상대가 남는다고 보고 각각 퇴근
읽기 이상 표만으로 충분하지 않은 이유SQL 표준의 전통적 표는 더티 리드·반복 불가능 읽기·팬텀 리드를 중심으로 수준을 정의하지만, 실제 애플리케이션에서는 갱신 분실과 쓰기 스큐처럼 읽기와 쓰기 의존성이 결합된 이상 현상도 중요합니다. 특정 수준이 안전한지는 업무 불변식과 DBMS 구현까지 봐야 합니다.

이상 현상과 격리 수준을 선택하면 허용·차단·중단 가능성을 타임라인으로 보여 줍니다.

표시는 교육용 일반화입니다. 실제 차단·중단 시점과 Repeatable Read 보장은 DBMS 및 SQL 문장 종류에 따라 다릅니다.

Four standard levels

낮은 수준에서 높은 수준으로 갈수록 “한 트랜잭션 안에서 허용하는 변화”가 줄어듭니다

격리 수준더티 리드반복 불가능 읽기팬텀 리드직관적 관찰 규칙
Read Uncommitted표준상 가능가능가능다른 트랜잭션의 미커밋 상태까지 볼 수 있는 가장 약한 수준. 일부 MVCC DBMS는 별도로 구현하지 않습니다.
Read Committed방지가능가능각 문장은 시작 시점에 커밋된 데이터의 스냅샷을 볼 수 있습니다. 다음 문장은 더 최신 커밋을 볼 수 있습니다.
Repeatable Read방지방지표준상 허용 가능트랜잭션의 일관된 관찰 범위를 유지하는 구현이 흔하지만 팬텀·갱신 충돌 보장은 제품마다 다릅니다.
Serializable방지방지방지성공한 동시 트랜잭션 결과가 어떤 직렬 실행 순서와 동등해야 합니다. 필요하면 대기 또는 중단·재시도가 발생합니다.

PostgreSQL을 예로 보면

PostgreSQL에서는 Read Uncommitted를 요청해도 Read Committed처럼 동작합니다. Read Committed는 문장마다 새 스냅샷을 사용할 수 있고, Repeatable Read는 트랜잭션 범위의 안정된 스냅샷을 제공하며 PostgreSQL 구현에서는 팬텀 읽기도 허용하지 않습니다. Serializable은 직렬화할 수 없는 의존성 패턴을 감지하면 트랜잭션 하나를 직렬화 실패로 중단할 수 있습니다.

표는 최소 금지 현상입니다표준이 어떤 현상을 “허용”한다고 적어도 DBMS는 더 강한 보장을 제공할 수 있습니다. 반대로 갱신 분실 같은 동작은 SELECT와 UPDATE 형태에 따라 달라집니다. 실제 사용 전에는 대상 DBMS와 쿼리 패턴으로 재현 시험을 해야 합니다.
Interactive SVG 02 · MVCC and snapshots

MVCC는 읽는 사람에게 데이터의 특정 시점 버전을 보여 주어 읽기와 쓰기의 충돌을 줄입니다

MVCC(Multi-Version Concurrency Control)는 행의 여러 버전과 트랜잭션 가시성 정보를 관리합니다. 읽기는 “현재 디스크의 마지막 값”을 무조건 보는 대신 자신의 스냅샷에서 보이는 버전을 선택합니다. 이 때문에 읽기와 쓰기가 항상 서로를 막지 않으면서도 미커밋 값을 숨길 수 있습니다.

Interactive SVG 02 · Statement versus transaction snapshot

T1이 같은 행을 두 번 읽는 사이 T2가 커밋하면 무엇을 보게 될까?

Read Committed와 Repeatable Read의 스냅샷 범위를 비교합니다.

실제 스냅샷 획득 시점은 DBMS와 첫 문장 종류에 따라 세부 차이가 있습니다. 여기서는 일반적인 PostgreSQL 관찰 모델을 단순화합니다.

MVCC가 모든 동시성 문제를 자동 해결하지는 않습니다

두 트랜잭션이 서로 다른 행을 수정하면서 여러 행에 걸친 조건을 깨뜨리는 쓰기 스큐는 각자 일관된 스냅샷만 봐도 발생할 수 있습니다. 또한 오래 열린 트랜잭션은 과거 버전 정리를 방해할 수 있고, 같은 행을 갱신할 때는 여전히 잠금과 충돌 처리가 필요합니다.

Serializable · Equivalent, not necessarily sequential

Serializable은 실제로 하나씩 실행하라는 명령이 아니라 성공 결과가 하나씩 실행한 것과 같아야 한다는 보장입니다

직렬 가능성은 동시 실행 결과를 어떤 직렬 순서의 결과와 동일하게 설명할 수 있는 성질입니다. DBMS는 2단계 잠금, 프레디케이트 잠금, 검증, 직렬화 가능 스냅샷 격리(SSI) 등 서로 다른 방법으로 이를 구현할 수 있습니다.

대기와 잠금으로 예방

충돌 가능 범위를 잠금으로 막아 한쪽을 기다리게 합니다. 안전하지만 경합·교착·잠금 범위 비용이 생길 수 있습니다.

동시 진행 후 위험 패턴 중단

스냅샷으로 진행시키되 직렬 순서를 만들 수 없는 의존성 패턴을 감지하면 한 트랜잭션을 중단합니다. 애플리케이션 재시도가 계약의 일부가 됩니다.

const MAX_ATTEMPTS = 5;

for (let attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {
  try {
    await db.transaction({ isolation: "serializable" }, async (tx) => {
      await executeBusinessOperation(tx, commandId);
    });
    break;
  } catch (error) {
    if (!isRetryableSerializationFailure(error) || attempt === MAX_ATTEMPTS) throw error;
    await sleep(withJitter(exponentialBackoff(attempt)));
  }
}
재시도 가능한 단위DBMS가 트랜잭션을 중단하면 단순히 마지막 SQL 한 문장만 다시 보내는 것이 아니라, 트랜잭션의 읽기와 의사결정 전체를 새 스냅샷에서 다시 수행해야 합니다. 외부 결제·메일·메시지 발행 같은 부작용은 멱등성 키와 outbox 등 별도 설계가 필요합니다.
Selection · Invariants and contention

격리 수준 선택은 “높을수록 좋다”가 아니라 지켜야 할 불변식과 충돌 패턴을 명시하는 일입니다

업무 패턴위험우선 고려할 방법확인할 것
단순 단일 행 증감조회 후 계산 시 갱신 분실원자적 UPDATE ... SET value=value+?, 조건부 갱신영향 행 수와 재시도
읽은 행을 기반으로 같은 행 수정동시 갱신 충돌행 잠금 또는 버전 열을 이용한 낙관적 동시성 제어대기 시간·충돌 빈도
여러 행에 걸친 합계·최소 인원 제약쓰기 스큐·팬텀Serializable, 명시적 잠금, 제약을 단일 행·유일 제약으로 모델링전체 트랜잭션 재시도 가능성
보고서·일관된 장시간 읽기문장마다 결과 변화Repeatable Read/스냅샷, 읽기 전용 트랜잭션오래된 스냅샷과 버전 유지 비용
고경합 예약·재고초과 예약·긴 대기조건부 UPDATE, 유일·CHECK 제약, 짧은 트랜잭션, 큐·직렬화실패를 정상 흐름으로 처리
설계 문장 템플릿“동시에 두 요청이 실행되어도 재고는 0 미만이 될 수 없다. 따라서 UPDATE ... WHERE stock >= quantity로 원자적 조건부 차감을 수행하고 영향 행 수가 0이면 품절로 처리한다.”처럼 불변식·경쟁 조건·실패 처리를 한 문장으로 연결합니다.

예제 1 · 더티 리드

롤백될 잔액을 근거로 알림을 보낸 경우

가시성
문제

T1이 잔액 100을 0으로 UPDATE했지만 아직 커밋하지 않았습니다. T2가 0을 읽어 “잔액 부족” 알림을 보낸 뒤 T1이 롤백했습니다. 이상 현상을 분류하고 어떤 수준에서 방지되는지 설명하세요.

풀이 보기
1
관찰 값의 상태

T2가 읽은 0은 아직 커밋되지 않았고 최종적으로 롤백되었습니다.

2
분류

미커밋 값을 읽은 더티 리드입니다.

3
방지

표준상 Read Committed 이상은 미커밋 값을 보이지 않게 하므로 방지합니다. 외부 알림은 커밋 후 발행하는 구조가 추가로 필요합니다.

정답: 더티 리드이며 Read Committed 이상에서 방지됩니다.
예제 2 · 반복 읽기

한 트랜잭션 안에서 주문 금액이 달라졌다

스냅샷 범위
문제

T1이 주문 금액 10,000원을 읽습니다. T2가 12,000원으로 수정·커밋한 뒤 T1이 같은 행을 다시 읽어 12,000원을 봅니다. 현상과 Read Committed/Repeatable Read의 차이를 설명하세요.

풀이 보기
1
분류

같은 행을 같은 트랜잭션에서 두 번 읽었는데 커밋된 타 트랜잭션 수정 때문에 값이 달라진 반복 불가능 읽기입니다.

2
Read Committed

문장마다 새 스냅샷을 사용할 수 있어 두 번째 SELECT가 12,000원을 볼 수 있습니다.

3
Repeatable Read

일반적인 트랜잭션 스냅샷 구현에서는 T1이 처음 본 10,000원 버전을 계속 보게 합니다.

정답: 반복 불가능 읽기이며, Read Committed에서는 가능하고 Repeatable Read는 이를 방지해야 합니다.
예제 3 · 갱신 분실

조회 후 더하기가 두 번 실행됐는데 한 번만 반영되었다

원자적 UPDATE
문제

카운터가 10입니다. T1과 T2가 모두 10을 읽고 각각 11을 계산해 UPDATE합니다. 최종값이 11이 되었습니다. 원인과 더 직접적인 해결 SQL을 제시하세요.

풀이 보기
1
분류

두 요청의 읽기-수정-쓰기 중 뒤 UPDATE가 앞 UPDATE 결과를 덮어 한 증가가 사라진 갱신 분실입니다.

2
연산을 DB 안에서 원자화

UPDATE counters SET value = value + 1 WHERE id = ?처럼 현재 행 값을 기준으로 한 문장에서 증가시킵니다.

3
복잡한 계산이면

행 잠금(SELECT ... FOR UPDATE) 또는 버전 열 조건(WHERE version=?)과 충돌 재시도를 사용합니다.

정답: 갱신 분실이며, 단순 증가에는 원자적 UPDATE가 가장 직접적입니다.
주의: 격리 수준만 올리는 것보다 데이터베이스가 한 문장으로 보장할 수 있는 연산으로 바꾸는 편이 단순하고 효율적인 경우가 많습니다.
예제 4 · 쓰기 스큐

마지막 당직 의사 한 명을 남겨야 한다

다중 행 불변식
문제

의사 A와 B가 모두 당직 중이며 최소 한 명은 남아야 합니다. T1은 B가 당직임을 보고 A를 off로, T2는 A가 당직임을 보고 B를 off로 바꿔 둘 다 커밋했습니다. 같은 행을 동시에 쓰지 않았는데 왜 문제가 생겼으며 어떻게 막을 수 있습니까?

풀이 보기
1
의존성

두 트랜잭션은 같은 전체 조건을 읽었지만 서로 다른 행을 썼습니다. 행 단위 쓰기 충돌은 없습니다.

2
분류

각 스냅샷에서는 상대가 남아 있어 개별 결정이 타당해 보이지만 함께 커밋하면 불변식이 깨지는 쓰기 스큐입니다.

3
해결

Serializable에서 위험 의존성을 감지해 하나를 중단시키거나, 당직 집합을 보호하는 잠금·대표 행을 두고 잠그거나, 제약을 데이터 모델로 강제합니다.

정답: 쓰기 스큐이며 다중 행 조건을 직렬화할 수 있는 방법과 전체 트랜잭션 재시도가 필요합니다.
예제 5 · 팬텀

“재고 부족 상품 수”가 두 번의 조회 사이에 늘었다

조건 집합
문제

T1이 SELECT COUNT(*) FROM products WHERE stock < 5를 실행해 3을 얻습니다. T2가 조건을 만족하는 새 상품을 삽입·커밋한 뒤 T1이 같은 쿼리로 4를 얻습니다. 무엇이 바뀐 것입니까?

풀이 보기
1
행 값이 아니라 집합 구성

처음 읽은 세 행의 값이 바뀐 것이 아니라 조건을 만족하는 새 행이 나타났습니다.

2
분류

같은 조건 범위에 행이 나타난 팬텀 리드입니다.

3
보장 확인

표준상 Repeatable Read는 팬텀을 허용할 수 있지만 PostgreSQL 같은 구현은 스냅샷으로 더 강한 보장을 제공합니다. 업무에서 집합을 근거로 쓰기까지 한다면 Serializable 또는 적절한 제약·잠금을 검토합니다.

정답: 팬텀 리드이며 행 집합에 대한 가시성 문제입니다.
예제 6 · 조건부 갱신

재고 3개에서 2개씩 두 주문이 동시에 들어왔다

불변식
문제

재고가 3개이고 두 요청이 각각 2개 구매를 시도합니다. 재고가 음수가 되지 않도록 단일 SQL 문장과 결과 처리 방식을 설계하세요.

풀이 보기
1
불변식

stock ≥ 0이어야 하며, 확인과 차감 사이에 다른 요청이 끼어들면 안 됩니다.

2
조건부 원자 갱신

UPDATE products SET stock=stock-2 WHERE id=? AND stock>=2를 실행합니다.

3
영향 행 수

1이면 성공, 0이면 이미 다른 주문이 차감했거나 재고 부족이므로 주문을 실패 처리합니다.

정답: 조건 확인과 차감을 한 UPDATE에 결합하고 영향 행 수를 비즈니스 결과로 해석합니다. 두 주문 중 하나만 성공해 최종 재고는 1입니다.
독립 연습
  1. Read Committed에서 한 트랜잭션의 두 SELECT가 서로 다른 커밋 상태를 볼 수 있는 이유를 설명하세요.
  2. 버전 열이 7인 행을 수정할 때 낙관적 동시성 제어 UPDATE 조건을 작성해 보세요.
  3. Serializable 오류를 받은 뒤 마지막 UPDATE만 재실행하면 안 되는 이유를 설명하세요.
연습 풀이 보기

1) 각 문장이 시작할 때 새 스냅샷을 얻을 수 있기 때문입니다. 2) 예: UPDATE ... SET ..., version=8 WHERE id=? AND version=7; 영향 행 수 0이면 다시 읽고 재시도합니다. 3) 이전 읽기와 의사결정이 오래된 스냅샷에 근거했으므로 트랜잭션 전체를 새 스냅샷에서 다시 계산해야 합니다.

Misconceptions and boundaries

격리 수준을 암기표로만 볼 때 생기는 오해

“Serializable은 모든 트랜잭션을 실제로 한 줄로 세운다”

충돌하지 않는 작업은 동시에 진행할 수 있습니다. 성공한 결과가 어떤 직렬 순서와 동등하도록 보장하며, 필요하면 대기나 중단이 일어납니다.

“격리 수준을 높이면 애플리케이션 동시성 버그가 모두 사라진다”

외부 시스템 부작용, 잘못된 불변식 모델링, 긴 트랜잭션, 재시도 부재, 중복 요청은 별도 문제입니다. 데이터베이스 제약과 멱등성 설계가 함께 필요합니다.

“MVCC는 잠금을 사용하지 않는다”

MVCC는 읽기 가시성을 버전으로 처리하지만 쓰기 충돌, DDL, 명시적 잠금 등에는 여전히 잠금이 사용됩니다.

“Repeatable Read는 모든 DBMS에서 같은 보장이다”

스냅샷과 팬텀 처리, 갱신 충돌이 제품마다 다릅니다. 이름이 아니라 대상 DBMS의 공식 문서와 재현 테스트를 기준으로 해야 합니다.

문서 범위이 문서는 관계형 DB의 기본 격리와 PostgreSQL 사례를 중심으로 합니다. 분산 트랜잭션, 선형화 가능성, 복제 지연, 분산 스냅샷, 락 모드 전체, 데드락 탐지, SSI 내부 알고리즘은 독립 문서로 분리하는 것이 적절합니다.

Reference concepts · Catalog nodes

참조되었지만 아직 독립 문서가 없는 개념

동일 concept ID는 문서 발행 후 자동으로 실제 경로로 전환됩니다.

트랜잭션(transaction)

데이터베이스 상태를 하나의 논리 작업 단위로 읽고 변경한 뒤 커밋하거나 롤백하는 실행 단위입니다.

proposed · transaction

직렬 스케줄

한 트랜잭션이 끝난 뒤 다음 트랜잭션이 실행되어 연산이 서로 섞이지 않는 스케줄입니다.

proposed · serial-schedule

더티 리드

아직 커밋되지 않아 롤백될 수 있는 다른 트랜잭션의 값을 읽는 현상입니다.

proposed · dirty-read

반복 불가능 읽기

같은 트랜잭션이 같은 행을 다시 읽었을 때 다른 트랜잭션의 커밋 때문에 값이 달라지는 현상입니다.

proposed · nonrepeatable-read

팬텀 리드

같은 조건 질의를 다시 실행했을 때 다른 트랜잭션의 삽입·삭제 때문에 결과 행 집합이 달라지는 현상입니다.

proposed · phantom-read

직렬화 실패

안전한 직렬 순서를 만들 수 없는 동시 실행을 데이터베이스가 감지해 트랜잭션 하나를 중단시키는 오류입니다.

proposed · serialization-failure

교착 상태

둘 이상의 트랜잭션이 서로가 보유한 자원을 기다려 누구도 진행할 수 없는 상태입니다.

proposed · deadlock

재시도

직렬화 실패나 교착 상태처럼 일시적 동시성 오류가 발생했을 때 전체 트랜잭션을 처음부터 다시 실행하는 전략입니다.

proposed · retry

갱신 분실

두 트랜잭션이 같은 이전 값을 바탕으로 갱신하여 한쪽 변경이 다른 쪽 변경에 덮이는 현상입니다.

proposed · lost-update

쓰기 스큐

서로 다른 행을 갱신하지만 같은 조건을 읽은 두 트랜잭션이 함께 커밋되어 전체 제약을 깨는 이상 현상입니다.

proposed · write-skew

Read Uncommitted

표준상 더티 리드를 허용할 수 있는 가장 낮은 트랜잭션 격리 수준입니다. 구현에 따라 더 강하게 동작할 수 있습니다.

proposed · read-uncommitted

Read Committed

각 문장이 시작할 때까지 커밋된 데이터만 보지만 같은 트랜잭션의 다음 문장은 새 커밋을 볼 수 있는 격리 수준입니다.

proposed · read-committed

스냅샷

특정 시점에 트랜잭션이 볼 수 있도록 고정된 데이터 버전의 집합입니다.

proposed · snapshot

Repeatable Read

트랜잭션 동안 이미 읽은 데이터가 바뀌어 보이지 않도록 더 안정적인 스냅샷을 제공하는 격리 수준입니다.

proposed · repeatable-read

Serializable

커밋된 동시 실행 결과가 어떤 직렬 실행과 동등하도록 보장하는 가장 강한 표준 격리 수준입니다.

proposed · serializable

MVCC

여러 버전의 행을 유지하여 읽기와 쓰기의 충돌을 줄이고 스냅샷 읽기를 제공하는 동시성 제어 방식입니다.

proposed · mvcc

직렬 가능성

동시 실행 결과가 어떤 직렬 실행 순서의 결과와 동등한 성질입니다.

proposed · serializability

프레디케이트 잠금

특정 행뿐 아니라 질의 조건에 영향을 줄 수 있는 쓰기 충돌을 추적하기 위한 논리적 잠금 개념입니다.

proposed · predicate-lock

잠금

다른 트랜잭션의 충돌하는 접근을 기다리게 하거나 막기 위해 데이터에 설정하는 동시성 제어 장치입니다.

proposed · lock

행 잠금

특정 행에 대한 충돌 갱신이나 잠금 요청을 직렬화하기 위해 설정하는 잠금입니다.

proposed · row-lock

낙관적 동시성 제어

충돌이 드물다고 가정하고 작업 후 버전 비교나 조건부 갱신으로 충돌을 감지하는 방식입니다.

proposed · optimistic-concurrency
