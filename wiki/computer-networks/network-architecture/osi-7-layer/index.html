OSI 7계층은 통신을 일곱 상자로 외우는 표가 아니라, 문제를 책임 단위로 나누는 참조 모델입니다

OSI 7계층은 서로 다른 시스템이 통신할 때 필요한 기능을 일곱 계층으로 나누어 설명합니다. 각 계층은 아래 계층이 제공하는 서비스를 사용하고, 위 계층에는 더 추상화된 서비스를 제공합니다.

핵심 질문“이 데이터가 실제 전선에서 어떤 신호가 되는가?”, “같은 링크의 다음 장치까지 어떻게 전달되는가?”, “여러 네트워크를 지나 목적지 호스트를 어떻게 찾는가?”, “목적지 프로그램까지 어떤 전달 계약을 제공하는가?”, “애플리케이션이 이해할 의미를 어떻게 표현하는가?”를 한꺼번에 풀지 않고 책임별로 나눕니다.
수직 관계서비스와 인터페이스

한 계층은 바로 아래 계층의 기능을 이용합니다. 경계에서 무엇을 요청하고 무엇을 돌려받는지가 인터페이스입니다.

수평 관계동료 프로토콜

송신 측과 수신 측의 같은 계층은 논리적으로 같은 규칙을 따릅니다. 이것을 동료 프로토콜 관계로 봅니다.

실제 이동캡슐화와 역캡슐화

송신 시 각 계층이 제어 정보를 붙이고, 수신 시 반대 순서로 해석합니다. 이를 캡슐화와 역캡슐화라고 합니다.

OSI 모델은 실제 인터넷 프로토콜을 모두 정확히 일대일로 배치하는 구현 명세가 아닙니다. 오히려 복잡한 통신 기능을 공통 언어로 설명하고, 설계·교육·장애 분석에서 어느 책임을 살펴볼지 좁히는 기준입니다.

Concept graph · What must connect

계층 이름보다 먼저 보아야 할 개념 관계

OSI 모델의 핵심은 “일곱 개”보다 서비스—인터페이스—프로토콜—캡슐화의 관계입니다. 아래 그래프는 각 계층과 주소·전달 단위를 함께 연결합니다.

Layer principles · Before memorization

한 계층을 이해하려면 네 가지를 묻습니다

무엇을 책임지는가?

예를 들어 네트워크 계층은 여러 링크를 지나 목적지 호스트까지 가는 경로와 논리 주소를 다룹니다.

위 계층에 어떤 서비스를 제공하는가?

전송 계층은 애플리케이션 프로세스 사이의 전달을 제공하며, TCP와 UDP는 서로 다른 전달 계약을 제공합니다.

같은 계층끼리 어떤 규칙을 공유하는가?

헤더 필드의 의미, 상태 전이, 오류 처리처럼 양 끝이 함께 지켜야 하는 규칙이 프로토콜입니다.

무엇을 붙이고 무엇을 읽는가?

각 계층은 상위 데이터에 자신이 해석할 제어 정보를 붙여 PDU를 만듭니다.

서비스와 프로토콜은 다릅니다

서비스는 위 계층이 얻는 능력입니다. 프로토콜은 그 서비스를 구현하기 위해 양 끝의 같은 계층이 따르는 규칙입니다. 사용자는 택배 서비스를 이용하지만, 물류 센터끼리는 내부 분류 규칙을 따르는 것과 비슷합니다.

계층 경계는 현실에서 완벽히 분리되지 않습니다

성능, 보안, 구현 편의를 위해 기능이 여러 계층에 걸치기도 합니다. 예를 들어 TLS는 응용과 전송 사이에서 보안 표현과 세션 성격의 기능을 함께 제공합니다. 모델은 사고를 돕는 지도이지 모든 구현의 정확한 해부도가 아닙니다.

The seven responsibilities

7계층부터 1계층까지: 각 계층이 답하는 질문

계층핵심 질문과 책임대표 정보·예전달 단위의 흔한 이름장애 단서
7. 응용사용자·애플리케이션이 원하는 네트워크 기능과 의미는 무엇인가?HTTP, DNS, SMTP 등데이터 또는 메시지잘못된 요청, 이름 해석, 권한·애플리케이션 오류
6. 표현양쪽이 같은 형식과 의미로 데이터를 해석할 수 있는가?문자 인코딩, 직렬화, 압축, 암호 표현깨진 문자, 형식 불일치, 인증서·암호화 협상 문제
5. 세션대화를 어떻게 시작·유지·동기화·복구할 것인가?대화 상태, 체크포인트, 재개, 세션 관리로그인 세션 만료, 대화 상태 손실, 재개 실패
4. 전송목적지의 어떤 프로세스에 어떤 전달 계약으로 보낼 것인가?포트, 순서·재전송·흐름 제어TCP 세그먼트 / UDP 데이터그램포트 차단, 연결 실패, 손실·재전송, 혼잡
3. 네트워크서로 다른 네트워크를 지나 어느 호스트로 갈 것인가?IP 주소, 라우팅, TTL패킷(IP 데이터그램)경로 없음, 잘못된 주소·게이트웨이, 라우팅 루프
2. 데이터 링크현재 링크에서 바로 다음 노드까지 프레임을 어떻게 전달할 것인가?MAC 주소, 프레임, 오류 검출, VLAN프레임스위치 포트·VLAN·무선 연결·프레임 오류
1. 물리비트를 전기·빛·전파의 신호로 어떻게 표현하고 전달할 것인가?매체, 커넥터, 전압·광·무선 신호, 변조·선로 부호비트 또는 심볼케이블 단선, 신호 세기, 커넥터·클록 문제

상위 세 계층이 인터넷 구현에서 흐릿해 보이는 이유

오늘날 인터넷 애플리케이션은 표현·세션 기능을 응용 프로토콜, 라이브러리, 런타임에 포함하는 경우가 많습니다. 그래서 실제 TCP/IP 모델에서는 OSI의 5~7계층을 하나의 응용 계층으로 묶어 설명하는 일이 흔합니다. 그렇다고 표현이나 세션이라는 책임이 사라지는 것은 아닙니다. 위치와 구현 주체가 달라질 뿐입니다.

장비를 계층 하나에만 가두지 않기스위치는 주로 2계층 전달을, 라우터는 주로 3계층 전달을 수행한다고 설명할 수 있습니다. 그러나 실제 장비에는 관리용 IP, ACL, 방화벽, 터널, 로드밸런싱 등 여러 계층 기능이 함께 들어갈 수 있습니다.
Interactive SVG 01 · Encapsulation

캡슐화는 데이터가 아래로 내려가며 “봉투 안의 봉투”가 되는 과정입니다

응용 데이터가 전송 계층으로 내려가면 전송 헤더가 붙고, 네트워크 계층에서는 IP 헤더가, 데이터 링크 계층에서는 링크 헤더와 경우에 따라 트레일러가 붙습니다. 수신 측에서는 반대 순서로 각 계층이 자신에게 해당하는 제어 정보를 해석해 제거합니다.

Interactive SVG 01 · Layered envelope

계층을 이동하며 데이터의 바깥 포장이 어떻게 바뀌는지 살펴보세요

송신 또는 수신 방향을 고르고 단계 슬라이더를 움직이면 현재 계층이 추가하거나 제거하는 정보를 강조합니다.

헤더 크기는 설명을 위한 단순화된 예시입니다. 실제 길이는 프로토콜 옵션, 주소 체계, 링크 종류에 따라 달라집니다.

주소도 계층마다 가리키는 대상이 다릅니다

2계층MAC 주소

현재 링크에서 프레임을 받을 인터페이스를 가리킵니다. 라우터를 지날 때 다음 링크에 맞춰 바뀔 수 있습니다.

3계층IP 주소

여러 네트워크를 건너 최종 호스트의 논리적 위치를 가리킵니다. 일반적인 전달에서 종단 주소는 유지되지만 NAT 같은 예외가 있습니다.

4계층포트 번호

호스트 안에서 데이터를 받아야 할 프로세스·통신 종단을 구분합니다. IP 주소만으로는 어느 애플리케이션인지 알 수 없습니다.

OSI and the Internet stack

OSI 7계층과 TCP/IP 모델은 목적이 같아 보여도 정확한 일대일 대응표가 아닙니다

OSI 참조 모델인터넷 계층 모델에서 흔한 묶음해석할 때의 주의점
7 응용 + 6 표현 + 5 세션응용표현·세션 책임이 사라진 것이 아니라 응용 프로토콜과 라이브러리에 통합됩니다.
4 전송전송TCP와 UDP처럼 종단 프로세스 간 서비스를 제공합니다.
3 네트워크인터넷IP를 중심으로 서로 다른 네트워크를 연결합니다.
2 데이터 링크 + 1 물리링크 또는 네트워크 접근이더넷·Wi‑Fi 같은 링크 기술과 실제 매체를 함께 묶어 설명하기도 합니다.

따라서 “HTTP는 무조건 7계층, TLS는 무조건 6계층”처럼 하나의 숫자만 정답으로 보는 것보다, 그 기능이 어떤 서비스를 제공하고 어느 헤더·상태를 해석하는가를 설명하는 편이 정확합니다.

Interactive SVG 02 · Troubleshooting

장애 분석에서는 아래에서 위로만 외우지 말고, 증거로 범위를 줄입니다

“인터넷이 안 된다”는 하나의 증상 안에는 케이블, 링크 연결, 주소 설정, 라우팅, 포트 차단, TLS 협상, DNS, 서버 애플리케이션 등 전혀 다른 원인이 들어 있습니다. OSI 모델은 원인을 자동으로 알려 주지 않지만, 어느 책임까지 정상임이 확인되었는지 정리하는 데 유용합니다.

Interactive SVG 02 · Evidence-driven diagnosis

증상을 선택해 조사 범위와 다음 검사를 확인하세요

한 증상은 여러 계층에서 발생할 수 있으므로 “가능성 높은 시작점”과 “확인으로 제외된 범위”를 함께 보여 줍니다.

ping 성공은 ICMP/IP 경로의 일부가 동작한다는 증거일 뿐, TCP 포트·TLS·HTTP 애플리케이션까지 정상이라는 뜻은 아닙니다.

실전에서 사용할 수 있는 증거 사다리

물리·링크 상태

인터페이스 up/down, 케이블·무선 연결, 링크 속도, 프레임 오류, VLAN을 확인합니다.

로컬 주소와 다음 홉

IP·서브넷·기본 게이트웨이, ARP/Neighbor Discovery, 같은 링크의 게이트웨이 도달 여부를 확인합니다.

원격 경로

라우팅 테이블, 경로 추적, 방화벽·ACL, TTL 소진 여부를 조사합니다.

전송 종단

목적지 포트가 열려 있는지, 서버가 listen 중인지, TCP 핸드셰이크와 재전송이 어떻게 보이는지 확인합니다.

이름·보안·애플리케이션

DNS 응답, TLS 인증서·협상, HTTP 상태 코드, 서버 로그와 요청 내용을 확인합니다.

예제와 풀이

정답 계층 번호만 고르는 대신, 관찰된 증거와 각 계층의 책임을 연결하는 연습입니다.

예제 1 · 캡슐화

브라우저의 HTTP 요청이 이더넷 프레임이 되기까지

전체 흐름
문제

같은 LAN 밖에 있는 서버로 브라우저가 HTTP 요청을 TCP/IPv4/Ethernet을 통해 보낸다고 가정합니다. 응용 데이터가 링크로 나가기까지 각 단계에서 무엇이 추가되는지 설명하세요.

풀이 보기
1
응용 계층

브라우저는 HTTP 메서드·경로·헤더·본문이라는 의미 있는 메시지를 만듭니다.

2
전송 계층

TCP는 출발·목적지 포트, 순서 번호와 제어 정보를 포함한 헤더를 붙여 바이트 스트림 일부를 세그먼트로 운반합니다.

3
네트워크 계층

IPv4는 출발·목적지 IP 주소 등을 포함한 헤더를 붙여 패킷을 만듭니다.

4
데이터 링크 계층

목적지가 다른 네트워크이므로 프레임의 목적지 MAC은 최종 서버가 아니라 현재 링크의 기본 게이트웨이 인터페이스가 됩니다. 이더넷 헤더와 오류 검출용 트레일러가 붙습니다.

5
물리 계층

프레임의 비트가 링크 기술에 맞는 전기·광·무선 신호로 표현됩니다.

핵심: HTTP 의미는 안쪽에 유지되고, TCP → IP → Ethernet 제어 정보가 바깥쪽에 차례로 붙습니다.
예제 2 · 장애 분석

ping은 되지만 HTTPS 접속이 되지 않는다

증거 기반
문제

서버 IP로 ping은 성공하지만 브라우저에서 https://server 접속이 실패합니다. 무엇이 이미 확인되었고, 다음으로 무엇을 확인해야 합니까?

풀이 보기
1
확인된 범위를 제한적으로 해석합니다.

적어도 일부 물리·링크·IP 경로와 ICMP 왕복이 동작한다는 증거입니다. 모든 경로나 모든 프로토콜이 정상이라는 뜻은 아닙니다.

2
4계층 연결을 분리해 검사합니다.

TCP 443 포트 연결 시도가 SYN에 응답하는지 확인합니다. 서버 listen 상태, 방화벽, ACL을 봅니다.

3
TCP가 되면 TLS와 응용 계층을 봅니다.

TLS 인증서·프로토콜 협상, SNI, 서버 이름과 인증서 일치, 이후 HTTP 응답과 서버 로그를 확인합니다.

결론: “ping 성공 → 네트워크 전체 정상”이 아니라, 3계층 일부까지의 증거를 얻었으므로 4계층부터 위로 검사를 이어 갑니다.
예제 3 · 주소

라우터를 한 번 지날 때 어떤 주소가 바뀌는가

L2와 L3
문제

호스트 A가 라우터 R을 거쳐 호스트 B에 IPv4 패킷을 보냅니다. NAT가 없다고 가정할 때 첫 번째 링크와 두 번째 링크에서 출발·목적지 MAC 주소와 IP 주소는 어떻게 됩니까?

풀이 보기
1
A → R 링크

프레임 MAC은 A의 인터페이스 → R의 A측 인터페이스입니다. 내부 IP 패킷은 A의 IP → B의 IP입니다.

2
라우터 처리

R은 첫 프레임을 제거하고 IP 헤더를 조사해 다음 홉을 선택합니다. TTL 같은 일부 IP 필드는 변경됩니다.

3
R → B 링크

새 프레임 MAC은 R의 B측 인터페이스 → B의 인터페이스입니다. NAT가 없으므로 내부 IP 출발·목적지는 여전히 A → B입니다.

정답: 링크 계층 주소는 홉마다 새로 정해지고, 종단 IP 주소는 일반적으로 유지됩니다.
대표 오해: “패킷 전체가 라우터를 그대로 통과한다”가 아니라, 링크 프레임은 각 홉에서 종료되고 새 프레임으로 다시 캡슐화됩니다.
예제 4 · 오버헤드

100바이트 응용 데이터의 단순화된 캡슐화 크기

계산
문제

옵션이 없는 TCP 헤더 20B, IPv4 헤더 20B, 단순화한 Ethernet 헤더·트레일러 합계 18B라고 가정합니다. 응용 데이터 100B가 한 세그먼트·패킷·프레임에 담길 때 프레임 내부 크기와 응용 데이터 비율을 구하세요. 프리앰블과 인터프레임 간격은 제외합니다.

풀이 보기
1
제어 정보 합계

20+20+18=58B입니다.

2
전체 크기

100+58=158B입니다.

3
응용 데이터 비율

100/158×100≈63.3%입니다.

정답: 158B, 그중 응용 데이터 약 63.3%
주의: 실제 Ethernet 최소 프레임, VLAN 태그, TCP 옵션, IP 버전, 터널과 링크 전송 오버헤드에 따라 값은 달라집니다. 문제의 가정을 먼저 고정해야 합니다.
예제 5 · 분류

DNS 이름 조회 실패는 몇 계층 문제인가

단일 숫자 거부
문제

원격 서버 IP에는 접속되지만 도메인 이름으로는 접속되지 않습니다. “7계층 문제”라고만 답하면 왜 부족하며 어떤 계층을 함께 확인해야 합니까?

풀이 보기
1
응용 의미

DNS는 이름을 주소로 바꾸는 응용 계층 프로토콜이므로 요청·응답 형식과 서버 설정은 응용 계층 책임입니다.

2
하위 전달 의존성

DNS 질의가 서버까지 가려면 UDP 또는 TCP의 포트, IP 경로, 링크 연결이 필요합니다. IP 접속이 된다는 증거는 일부 하위 범위를 줄이지만 DNS 서버 주소·포트·방화벽은 여전히 확인해야 합니다.

3
결론

주된 기능은 7계층에 속하지만 장애 원인은 계층 경계를 넘어설 수 있으므로 패킷 캡처, 설정, 서버 응답을 통해 실제 실패 지점을 확인합니다.

정답: 계층 번호는 시작점이며, 증거를 통해 DNS 애플리케이션과 전송·네트워크 경로를 분리해 검사해야 합니다.
독립 연습
  1. 같은 스위치에 연결된 두 호스트가 통신할 때 2계층과 3계층이 각각 수행하는 역할을 설명하세요.
  2. TCP 연결은 성공했지만 수신한 JSON을 파싱하지 못한다면 어느 책임을 우선 살펴보아야 합니까?
  3. 케이블을 교체하자 통신이 정상화되었습니다. 이것이 상위 계층 설정이 올바르다는 것을 완전히 증명합니까?
연습 풀이 보기

1) 3계층 주소로 종단 호스트를 식별하되 같은 서브넷이라면 라우터 없이 2계층 프레임으로 상대 인터페이스에 전달합니다. 2) 표현 형식·인코딩·스키마와 응용 메시지 계약을 우선 확인합니다. 3) 물리 원인이 하나 제거되었다는 뜻이며, 다른 환경이나 경로에서 상위 설정 문제가 없다는 보장은 아닙니다.

Misconceptions and boundaries

계층 암기에서 자주 생기는 오해

“데이터가 실제로 7개의 독립 서버를 차례로 지난다”

한 종단 시스템 내부에서 데이터가 계층별 처리 단계를 거치는 논리 모델입니다. 중간 장치는 필요한 계층까지만 해석할 수 있으며, 모든 계층이 물리적으로 분리된 장비를 뜻하지 않습니다.

“각 프로토콜은 오직 하나의 계층에만 정확히 들어간다”

모델에 배치해 주된 책임을 설명할 수는 있지만, TLS·터널·NAT·로드밸런서처럼 여러 책임이 겹치는 구현이 많습니다. 기능과 인터페이스를 함께 설명해야 합니다.

“스위치는 2계층, 라우터는 3계층이므로 다른 계층은 전혀 모른다”

전통적 주 기능을 설명하는 말입니다. 실제 장비는 관리, 보안, 가상화, 애플리케이션 인식 기능을 함께 가질 수 있습니다.

“ping이 되면 1~7계층이 모두 정상이다”

ping은 특정 ICMP/IP 왕복에 대한 증거입니다. 포트, TCP 상태, TLS, DNS, HTTP 애플리케이션은 별도로 실패할 수 있습니다.

문서 범위이 문서는 OSI 기본 모델과 장애 분석 사고법을 다룹니다. Ethernet 프레임 형식, IPv4/IPv6 라우팅, ARP·Neighbor Discovery, TCP 상태 기계, DNS·HTTP·TLS는 각각 독립 문서로 확장하는 것이 적절합니다.
