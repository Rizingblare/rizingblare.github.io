TCP와 UDP의 차이는 “속도”가 아니라 애플리케이션에 약속하는 전달 방식입니다

TCP와 UDP는 모두 전송 계층에서 호스트 안의 특정 프로세스를 포트 번호로 구분해 데이터를 전달합니다. 그러나 TCP는 신뢰적이고 순서가 보장되는 바이트 스트림을 제공하고, UDP는 메시지 경계를 유지하는 최소한의 데이터그램 전달을 제공합니다.

TCP의 질문

“보낸 바이트를 빠짐없이 같은 순서로 읽게 할 것인가?”

순서 번호, ACK, 재전송, 흐름 제어, 혼잡 제어를 사용해 애플리케이션에 연속된 바이트 흐름을 제공합니다.

UDP의 질문

“각 메시지를 최소한의 전송 서비스로 독립 전달할 것인가?”

연결 설정, 순서 정렬, 재전송, 혼잡 제어를 UDP 자체가 제공하지 않습니다. 필요한 보장은 애플리케이션 또는 UDP 위의 다른 프로토콜이 설계합니다.

“UDP가 빠르다”는 문장의 한계UDP 헤더와 상태는 단순하지만 실제 지연과 처리량은 네트워크, 메시지 크기, 손실률, 애플리케이션의 복구 방식에 달려 있습니다. UDP 위에 신뢰성·암호화·혼잡 제어를 구현하면 비용이 생깁니다. 반대로 TCP 연결을 재사용하고 손실이 적다면 연결 설정 비용은 전체 작업에서 작을 수 있습니다.

흐름 제어수신자가 받을 수 있는 범위를 알림없음UDP 송신 애플리케이션이 수신 처리 능력을 고려해야 합니다.
혼잡 제어네트워크 혼잡 신호에 따라 전송량 조절UDP 자체에는 없음UDP 기반 애플리케이션도 인터넷에서 공정하고 안전한 혼잡 제어를 설계해야 합니다.
헤더기본 20바이트 이상, 옵션 가능기본 8바이트작은 메시지에서는 상대 차이가 크지만 전체 시스템 비용은 헤더만으로 결정되지 않습니다.
TCP operation · Reliability as mechanisms

TCP의 “신뢰성”은 손실이 없다는 뜻이 아니라 손실을 감지하고 복구하는 과정입니다

1. 연결 설정: 양쪽의 시작 상태를 맞춥니다

3-way handshake는 일반적으로 SYN → SYN+ACK → ACK의 세 단계로 양쪽이 서로의 초기 순서 번호를 확인하고 송수신 상태를 준비합니다. 이것은 경로 전체를 예약하는 절차가 아니라 종단 TCP 상태를 동기화하는 과정입니다.

2. 순서 번호와 ACK: 바이트 위치를 추적합니다

TCP 순서 번호는 “패킷 번호”라기보다 바이트 스트림에서 해당 세그먼트의 첫 바이트 위치를 가리킵니다. 수신자의 누적 ACK 값은 일반적으로 “다음에 기대하는 바이트 번호”를 뜻합니다. 예를 들어 순서 번호 1,000부터 500바이트를 정상 수신했다면 ACK 1,500을 보낼 수 있습니다.

3. 재전송: 확인되지 않은 범위를 다시 보냅니다

송신자는 타이머 만료나 중복 ACK 같은 신호를 통해 손실 가능성을 판단하고 재전송합니다. 수신자는 이미 받은 중복 바이트를 순서 번호로 식별해 애플리케이션에 중복 전달하지 않습니다.

4. 흐름 제어와 혼잡 제어는 서로 다른 병목을 봅니다

흐름 제어

수신 호스트의 버퍼와 처리 능력을 보호합니다. 수신 윈도우는 “내가 지금 더 받을 수 있는 양”을 알립니다.

혼잡 제어

네트워크 경로의 혼잡을 완화합니다. 손실·지연·ECN 같은 신호에 따라 송신 속도와 비행 중 데이터 양을 조절합니다.

Interactive SVG 01 · Sequence, ACK and retransmission

한 세그먼트가 사라졌을 때 수신 순서와 ACK가 어떻게 변하는가

손실시킬 세그먼트와 세그먼트 크기를 바꾸어 타임라인을 확인하세요.

실제 TCP는 선택적 확인(SACK), 지연 ACK, 재정렬, 혼잡 제어 알고리즘에 따라 더 복잡할 수 있습니다. 이 도식은 누적 ACK와 재전송의 핵심 관계를 단순화합니다.

Head-of-line blocking뒤의 세그먼트가 먼저 도착해도 앞의 바이트가 빠져 있으면 TCP 바이트 스트림은 애플리케이션에 순서대로 전달해야 합니다. 이 대기 현상을 Head-of-line blocking 관점에서 이해할 수 있습니다.
UDP operation · Minimal datagrams

UDP는 기능이 없는 프로토콜이 아니라, 기능을 강제하지 않는 작은 전송 단위입니다

UDP 데이터그램 헤더에는 출발 포트, 목적지 포트, 길이, 체크섬이 있습니다. 데이터그램 하나는 수신 시 하나의 메시지 경계로 관찰됩니다. 그러나 데이터그램이 도착하지 않거나, 순서가 바뀌거나, 중복될 수 있으며 UDP는 이를 바로잡지 않습니다.

장점적은 강제 상태

연결 설정과 종단별 재전송 상태를 UDP 자체가 만들지 않아 단순한 질의·응답이나 상위 프로토콜의 기반으로 쓰기 쉽습니다.

책임애플리케이션이 선택

늦은 데이터는 버릴지, 재전송할지, 최신 값으로 덮을지 요구에 맞춰 정합니다.

주의혼잡 제어 필요

UDP 자체에 없다고 해서 무제한 송신해도 된다는 뜻은 아닙니다. 인터넷을 사용하는 프로토콜은 혼잡에 반응해야 합니다.

예를 들어 QUIC은 UDP 위에서 연결, 암호화, 신뢰적 스트림, 혼잡 제어 등을 별도로 구현합니다. 이는 “UDP이므로 신뢰성이 없다”가 아니라 UDP가 그 보장을 제공하지 않고 상위 프로토콜이 제공한다는 좋은 사례입니다.

Interactive SVG 02 · Framing

TCP의 가장 실용적인 차이: 보낸 메시지 단위가 그대로 수신 호출에 나타나지 않습니다

송신자가 "HELLO"와 "WORLD"를 두 번 보냈더라도 TCP 수신자는 "HELLOWORLD"를 한 번에 읽거나, "HE"와 "LLOWOR"와 "LD"로 나누어 읽을 수 있습니다. TCP가 보장하는 것은 바이트 순서이지 애플리케이션 메시지 경계가 아닙니다.

Interactive SVG 02 · Send calls versus receive units

같은 두 메시지가 TCP 스트림과 UDP 데이터그램에서 어떻게 보이는지 비교하세요

수신 버퍼 크기를 바꾸면 TCP 읽기 경계가 달라지지만 UDP 메시지 경계는 유지됩니다.

UDP에서도 수신 버퍼가 데이터그램보다 작으면 API와 구현에 따라 잘리거나 오류 정보가 제공될 수 있습니다. 핵심은 서로 다른 데이터그램이 TCP처럼 하나의 바이트 스트림으로 합쳐지지 않는다는 점입니다.

TCP 메시지 프레이밍의 대표 방법

고정 길이

모든 레코드 크기가 같을 때 단순하지만 가변 데이터에는 낭비가 생깁니다.

길이 접두어

앞의 고정 크기 필드에 본문 길이를 적습니다. 부분 읽기를 누적해 정확한 길이만큼 조립합니다.

구분자·자기 기술 형식

개행 같은 구분자 또는 파싱 가능한 포맷을 사용하되 이스케이프와 최대 길이 제한이 필요합니다.

예제 1 · 바이트 스트림

두 번 send 했으니 두 번 recv 하면 되는가

프레이밍
문제

송신자가 TCP로 send("ABC")와 send("DEF")를 호출했습니다. 수신자가 한 번의 recv(6)로 받을 수 있는 합법적인 결과 예를 들고, 두 메시지를 안전하게 복원하는 방법을 설명하세요.

풀이 보기
1
TCP 보장 확인

바이트 순서는 ABCDEF로 유지되지만 송신 호출 경계는 보존되지 않습니다.

2
가능한 읽기

한 번에 ABCDEF를 받을 수도 있고, 먼저 AB만 받은 뒤 나머지를 다음 호출에서 받을 수도 있습니다.

3
프레이밍

각 메시지 앞에 길이를 붙이거나 구분자를 사용하고, 수신 버퍼에 누적해 완전한 메시지가 될 때까지 반복해서 읽습니다.

결론: TCP는 메시지가 아니라 순서 있는 바이트를 전달하므로 애플리케이션 프레임이 필요합니다.
예제 2 · 순서 번호

ACK 번호 계산

기초 계산
문제

TCP 수신자가 순서 번호 1,000에서 시작하는 500바이트 데이터와 이어서 순서 번호 1,500에서 시작하는 300바이트 데이터를 모두 정상적으로 받았습니다. 다음에 기대하는 바이트를 나타내는 누적 ACK는 얼마입니까?

풀이 보기
1
첫 범위

1,000부터 499바이트 뒤까지이므로 다음 기대 번호는 1,500입니다.

2
두 번째 범위

1,500부터 300바이트를 받았으므로 다음 기대 번호는 1,800입니다.

정답: ACK 1,800
대표 오답: 세그먼트 개수 2를 더하는 것이 아니라 바이트 수만큼 순서 공간이 진행합니다. SYN과 FIN은 별도 순서 공간을 소비한다는 세부 규칙도 있습니다.
예제 3 · 손실

두 번째 세그먼트가 사라지고 세 번째가 먼저 도착했다

재전송
문제

각 400바이트인 세그먼트가 순서 번호 1,000, 1,400, 1,800으로 전송됩니다. 두 번째가 손실되고 세 번째가 도착했다면 누적 ACK 방식의 수신자는 일반적으로 어떤 ACK를 반복하며, 애플리케이션 전달은 왜 대기할 수 있습니까?

풀이 보기
1
첫 세그먼트 후

1,000~1,399를 받았으므로 다음 기대 번호 1,400을 ACK합니다.

2
세 번째가 먼저 도착

1,400~1,799가 비어 있으므로 누적 ACK는 여전히 1,400입니다. 세 번째 데이터를 임시 저장할 수 있어도 연속 범위는 늘지 않습니다.

3
재전송 후

누락 세그먼트가 도착하면 1,000~2,199가 연속되므로 ACK 2,200으로 진행할 수 있습니다.

정답: ACK 1,400을 반복하며, 바이트 스트림의 순서를 지키기 위해 빈 구간이 채워질 때까지 뒤 데이터를 애플리케이션에 보류할 수 있습니다.
예제 4 · UDP 설계

센서의 최신 온도값은 재전송해야 하는가

요구 분석
문제

예제 5 · 헤더 비용

20바이트 페이로드에서 TCP와 UDP 헤더 비율

가정 명시
문제

IP 헤더와 링크 오버헤드는 제외하고, 옵션 없는 TCP 헤더 20B와 UDP 헤더 8B만 비교합니다. 페이로드 20B일 때 전송 계층 PDU에서 헤더가 차지하는 비율을 각각 구하세요.

풀이 보기
1
TCP

전체 20+20=40B, 헤더 비율 20/40=50%입니다.

2
UDP

전체 8+20=28B, 헤더 비율 8/28≈28.6%입니다.

정답: TCP 50%, UDP 약 28.6%
해석 주의: 이 결과만으로 애플리케이션 성능을 결론 내릴 수 없습니다. TCP 연결 재사용, ACK, 재전송, UDP 애플리케이션 헤더와 자체 보장 비용까지 전체 트래픽을 측정해야 합니다.
예제 6 · 선택

대용량 파일과 실시간 게임 위치 업데이트

전이 문제
문제

① 한 바이트라도 틀리면 안 되는 대용량 파일 전송과 ② 매 50ms 최신 위치가 오며 오래된 위치는 폐기 가능한 게임 업데이트에 대해 적합한 전송 접근을 비교하세요.

풀이 보기
1
파일

완전성·순서가 필수이고 늦은 데이터도 가치가 있으므로 TCP의 신뢰적 스트림이 자연스럽습니다. 응용 수준 무결성 검증도 추가할 수 있습니다.

2
위치 업데이트

최신성이 중요하고 오래된 재전송이 지연을 늘릴 수 있으므로 UDP 기반 메시지와 번호·시각·보간·손실 정책이 적합할 수 있습니다.

3
단순 이분법을 피합니다.

게임의 로그인·결제·채팅은 TCP 또는 신뢰 스트림을, 위치 업데이트는 부분 신뢰 메시지를 쓸 수 있습니다. 하나의 애플리케이션이 여러 계약을 함께 사용합니다.

결론: 파일은 정확성 중심 TCP, 위치는 최신성 중심 UDP 기반 설계가 합리적이지만 기능별 요구를 분리해야 합니다.
독립 연습
  1. 순서 번호 5,000에서 1,200바이트를 연속 수신했다면 다음 ACK는 얼마입니까?
  2. UDP 데이터그램 A와 B를 차례로 보냈을 때 수신자는 어떤 결과들을 관찰할 수 있습니까?
  3. TCP 위에서 4바이트 길이 접두어를 쓰는 이유를 설명하세요.
연습 풀이 보기

1) ACK 6,200입니다. 2) A·B 모두 순서대로, B만, A만, 둘 다 손실, B가 A보다 먼저, 중복 등이 가능하며 UDP 자체는 수정하지 않습니다. 3) 스트림에서 메시지 경계가 사라지므로 먼저 길이를 읽고 정확히 그만큼 바이트를 누적해 하나의 메시지를 복원하기 위해서입니다.

Misconceptions and boundaries

TCP·UDP 비교에서 자주 틀리는 문장

“TCP는 패킷을 보내고 UDP도 패킷을 보낸다”

IP 수준에서는 둘 다 IP 데이터그램에 실릴 수 있지만 애플리케이션이 받는 계약이 다릅니다. TCP는 바이트 스트림이고 UDP는 데이터그램 메시지입니다.

“TCP는 손실이 발생하지 않는다”

네트워크 손실은 발생합니다. TCP는 이를 감지해 재전송하고 순서를 복구하려고 하므로 애플리케이션이 손실을 직접 보지 않게 만드는 것입니다. 연결이 끊기면 미확인 데이터의 최종 전달 여부를 애플리케이션이 알 수 없는 경우도 있습니다.

“UDP는 언제나 TCP보다 지연이 작다”

UDP 자체의 절차는 적지만 애플리케이션 재전송, 암호화, 혼잡 제어, NAT 경로, 패킷 크기와 손실이 실제 지연을 좌우합니다.

“신뢰성이 필요하면 무조건 TCP 하나면 된다”

다중 독립 스트림, 부분 신뢰성, 메시지별 만료가 필요하면 TCP 한 스트림의 순서 대기가 맞지 않을 수 있습니다. 검증된 QUIC 같은 상위 전송을 고려할 수 있습니다.

문서 범위이 문서는 기본 서비스 계약과 핵심 메커니즘을 다룹니다. TCP 상태 기계, RTT/RTO 계산, SACK, 혼잡 제어 알고리즘, UDP 체크섬 세부, NAT traversal, QUIC·HTTP/3는 독립 문서로 확장하는 것이 적절합니다.

proposed · udp

순서 번호

데이터 위치를 식별하여 순서 복원, 중복 검출, 손실 탐지를 돕는 번호입니다.

proposed · sequence-number

ACK

상대가 어느 위치까지 데이터를 정상적으로 받았는지 알리는 확인 정보입니다.

proposed · acknowledgment

재전송

손실되거나 손상된 것으로 판단된 데이터를 다시 보내는 복구 동작입니다.

proposed · retransmission

흐름 제어

빠른 송신자가 느린 수신자의 버퍼를 넘치게 하지 않도록 송신량을 조절하는 기능입니다.

proposed · flow-control

혼잡 제어

네트워크 경로의 수용 능력과 혼잡 신호에 맞춰 송신 속도를 조절하는 기능입니다.

proposed · congestion-control

메시지 경계

애플리케이션이 한 번에 보낸 데이터 단위의 시작과 끝이 수신 측에도 구분되는 성질입니다.

proposed · message-boundary

연결 지향

데이터 전송 전에 양 끝이 상태를 만들고 연결 수명 동안 그 상태를 유지하는 방식입니다.

proposed · connection-oriented

3-way handshake

TCP 양 끝이 SYN, SYN+ACK, ACK를 교환해 초기 순서 번호와 연결 상태를 동기화하는 절차입니다.

proposed · three-way-handshake

Head-of-line blocking

앞쪽 데이터가 도착하지 않아 뒤쪽에 도착한 데이터까지 애플리케이션에 전달되지 못하는 현상입니다.

proposed · head-of-line-blocking

UDP 데이터그램

UDP 헤더와 하나의 응용 메시지로 구성되는 전송 단위입니다.

proposed · udp-datagram

체크섬

전송 중 비트 오류가 발생했는지 검출하기 위해 헤더와 데이터에서 계산하는 짧은 검사용 값입니다.

proposed · checksum

QUIC

UDP 위에서 암호화, 신뢰성, 다중 스트림, 혼잡 제어 등을 구현하는 현대적 전송 프로토콜입니다.
